## 显示方式（2026-11-04 起：两条通道、六个实测过的档位）

游戏是 DirectDraw。名字一律写成「**模式（哪一层 + 哪种渲染）**」，
这样一眼能看出这档到底走什么路（用户定案，不再用「稳定/直连」这种看不懂的词）。

| 档 | 名字 | 层 / 配置 | 说明 |
|---|---|---|---|
| 1 | 软件画面 GDI（全屏） | `_cnc-ddraw\ddraw.dll` + `_presets\ddraw.ini` | Windows 自带 2D 画图（CPU），不碰显卡 3D 驱动。**网吧工单 YW027 的 `0xC0000094` 正是在这档出现的**，所以不写「最稳」 |
| 2 | 软件画面 GDI（4:3黑边） | `_presets\ddraw-43.ini` | `maintas=true`，人物不被拉胖 |
| 3 | 软件画面 GDI（窗口1280×720） | `_presets\ddraw-window.ini` | 方便 Alt-Tab，躲开 HDR/多显示器/覆盖层；除零类闪退的兜底档 |
| 4 | 原版640×480（窗口） | `_presets\ddraw-640.ini` | 原汁原味 |
| 5 | DX9硬件加速（全屏） | `_presets\ddraw-d3d9.ini` | 同样经 cnc-ddraw，但把游戏的 Blt 交给显卡 D3D9 画（GDI 太慢/太糊时试）；**不叠 DXVK** |
| 6 | dgVoodoo2转换（无边框全屏） | `_dgvoodoo2\ddraw.dll` + `_presets\dgVoodoo-window.conf` | **默认档（2026-11-04 用户定）**：换一层转译（输出走 D3D11）；`兼容修复.bat` 装完就顶在这一档，启动器收尾也回到这一档 |

命名是用户从四套方案里选的 B 套：**大白话说清「这档干什么」，括号/后缀保留技术名（GDI / DX9 / dgVoodoo2）方便远程核对**。
反例一：我先前自创的「稳定全屏」「直连模式」「加速模式」——看不出走什么路，已被否掉。
反例二（2026-11-04 用户再纠正）：第 1 档原来写「最稳·全屏」、文案里写「最兼容」——
**默认档恰恰是玩家实际崩掉的那一档，保证词是假的**；现在只写「是什么」，
稳不稳由启动器的现场快照 + 自动改窗口 + 记忆档位去兜，不靠界面承诺。
反例三（2026-11-04 用户第三次纠正）：第 6 档原来写「（窗口）」，实际**不是窗口**——
实测游戏窗口矩形 `0,0 800x600` 铺满整屏、style `0x14000000`（无标题栏、无边框、非 WS_POPUP）、
exstyle `0x8`（置顶），桌面当时也被切到 800×600。`_presets\dgVoodoo-window.conf` 里的
`FullScreenMode=false` 只是 dgVoodoo 自己不独占显示模式，不等于玩家看到的是窗口。
**名字要跟实测一致**，所以改成「无边框全屏」。
对照：预设里只有 `fullscreen=false` 的第 3、4 档是真窗口（截图能看到桌面），
`fullscreen=true` 的第 1、2、5 档铺满屏幕。

要点：

- **一层顶在 `ddraw.dll` 的位置上**：选 cnc 档就复制 `_cnc-ddraw\ddraw.dll`，选 dgVoodoo 档就复制 `_dgvoodoo2\ddraw.dll`；
  同时只保留该层的配置（cnc 用 `ddraw.ini`，dgVoodoo 用 `dgVoodoo.conf`），另一份删掉，避免残留互相干扰。
  游戏退出后**恢复成默认档（第 6 档 dgVoodoo2）**，缺 `_dgvoodoo2\ddraw.dll` 时才退回 cnc-ddraw GDI；
  收尾同样只留一层的一份配置，不在机器上留两层叠着的现场。
- **默认档 = 第 6 档 dgVoodoo2（2026-11-04 用户定）**：exe 初始选项、`game_starter.bat` 直接回车、
  `/go` 零交互、`兼容修复.bat` 落地状态四处一致（实测日志：`点「启动游戏」：6 dgVoodoo2转换（无边框全屏）`
  → `已挂载 dgVoodoo2 + dgVoodoo-window.conf` → `收尾回到默认档`）。
  兜底链不变：现场快照发现能当除数的 0 → 本次改用第 3 档；开局 25 秒内系统级异常退出 → 自动改第 3 档重试一次；
  跑满 45 秒 → 把这台机器实际生效的档写进 `显示方式记忆.txt`，下次直接用它。
- **撤掉的档位（记录，不用）**：
  - `dgVoodoo2 全屏`：实测通过启动器路径稳定复现游戏自己的报错框
    `DirectDraw Error (150): 'DDERR_INVALIDRECT'  File: 'D:\Source_Code\Game\WINGRAPH.CPP'  Line: 456`
    （同一份 conf 直接双击 `Heroes3.exe` 反而能进，说明和全屏时的主表面矩形校验有关，不是简单调键能稳的）；
    预设文件与菜单项都已删除，只留窗口档。证据：`evidence\mode6-probe.png`（报错框实拍）。
  - `renderer=opengl`：本机无硬件 OpenGL（只有 GL 1.1 / GDI Generic），包内说明也记录它容易黑屏/崩。
  - `renderer=auto`：先试 direct3d9，崩了来不及换别的；**不提供，也不往本游戏目录放 `d3d9.dll`/`dxgi.dll`（DXVK）**。
- **水印保留显示**（用户定案 2026-11-04）：`dgVoodooWatermark = true`，cnc-ddraw 的 logo 也用默认值——
  水印本身就是一个「当前走的是哪条通道」的可视标识。
- 高刷屏继续锁 `maxfps=60` / `FPSLimit=60` + 垂直同步，防止 1999 年的计时器随刷新率跑飞。

## 2026-11-04 网咖崩溃工单：`0xC0000094`（义乌网咖西钢店 YW027）

**工单原文要点**：`X:/YunGame/E/Heroes3/game_starter.exe` 运行 10 秒后异常退出，退出码 `0xC0000094`；
机器 Windows 11 LTSC 26200 + i5-14490F + RTX 4070 SUPER（驱动 610.88）+ 32GB；
磁盘表里 `A: 剩 1/5GB`、`B: 剩 0/0GB`、`X: 剩 4053/42923GB`（无盘/网络大盘）；开机 4 分钟，当天第 1 次启动；
峰值内存 38 MB。

**先分清是谁崩的**：`0xC0000094 = STATUS_INTEGER_DIVIDE_BY_ZERO`（整数除零）。
38 MB 是启动器自己的量级（游戏进地图会远大于这个数），而我们的启动器按平台契约
**把游戏退出码原样回传**，所以工单里挂的名字是 `game_starter.exe`，**崩的是 `Heroes3.exe` 本体**。
启动器里也没有会被喂 0 的整数除法（只有 `g.DpiX / 96f` 这种常量除数和 `/ 2`），
.NET 自己炸也不会报 `0xC0000094`（会是 `0xE0434352`）。

**除数从哪来（二进制证据，`tools\import-probe.py`）**：`Heroes3.exe` 的导入表里有
`GetDeviceCaps` 和 `GetDiskFreeSpaceA`（还有 `timeGetTime`、`ReadFile`），二进制里同时有字符串
`CDDrive` 和 `GetDiskFreeSpace`。1999 年的写法是拿这些返回值直接当除数且不判错：

- `GetDeviceCaps(hdc, VREFRESH)` 在现代驱动上常返回 0 → `xxx / 刷新率` 炸；
- `GetDiskFreeSpaceA` 失败时四个出参全是 0 → `xxx / (每扇区字节 × 每簇扇数)` 炸。
  这台机器的游戏在 `X:`（无盘网络卷），系统还报出 `A:`/`B:` 盘符（虚拟或误报，不是软驱；`B:` 总量 0），
  正是最容易让这两个调用返回 0 的环境；我们开发机是本地 `D:` + 正常显示器，所以一直复现不了。

**本次改动（启动器，44 KB）**：

1. **现场快照**：每次启动前把 `显示 宽×高 / 刷新率 / DPI / 屏幕数` + `游戏盘 每扇区字节 / 每簇扇数 / 簇数`
   + `A:`/`B:` 的同样数值 + 注册表 `AppPath`/`CDDrive` 全部写进 `运行日志.txt`。
   下次再报崩溃，日志里就能看到那台机器到底哪个是 0。
   本机实测一行：`现场快照：显示 1920×1080 刷新率=16384 DPI=96/96 屏幕数=1；游戏盘 D:\ 每扇区字节=512 每簇扇数=8 …；AppPath=D:\YunGame\E\Heroes3\ CDDrive=D:`
   （注意：`GetDiskFreeSpaceA` 的出参顺序是「每簇扇数在前、每扇区字节在后」，第一版我把标签写反了，已修）。
2. **自动兜底**：只要快照里出现能当除数的 0（刷新率≤0、桌面尺寸≤0、每扇区字节/每簇扇数=0），
   本次直接改用「3 窗口模式（1280×720）」——窗口模式不走全屏显示模式那条路，绕开刷新率来源；
   界面状态写「已自动改用窗口画面，避免闪退」，玩家能看懂，术语只进日志。
3. **异常早退重试**：游戏若在 25 秒内以系统级异常码（`>= 0xC0000000`）退出且当前不是窗口模式，
   自动改用窗口模式再试一次；跑满 45 秒就把这台机器实际生效的画面方式写进
   `显示方式记忆.txt`，下次开机直接用它（该文件是运行期状态，**不随交付包分发**，也不属于游戏数据）。
4. **顺带修掉一个静默失效**：`build.ps1` / `build-release.ps1` 把 nircmd 复制成了 `ircmdc.exe`，
   而 bat 里调的是 `_tools\nircmd\nircmdc.exe` —— 名字不一致导致 `if exist` 直接跳过，控制台窗口居中一直没生效。
   现在两处都落成 `nircmdc.exe`，构建时删掉旧的错名文件，manifest 同步（AGENTS 规则 8 要求逐字一致）。

**给店端的临时自救**：让玩家在启动器里选「3 窗口模式」或「4 原版 640×480（窗口）」启动；
`game_starter.bat` 菜单里同样是第 3/4 项。

**还缺的决定性证据**：故障模块 + 偏移。让店端不用改系统设置就能取到——
事件查看器 → Windows 日志 → 应用程序 → 那条 `Application Error`（会写 `Heroes3.exe` 还是 `ddraw.dll` + 偏移），

### 2026-11-07 追查：我们自己的快照把刷新率读错了

客户机日志（X:\YunGame\E\Heroes3，2560×1440）显示：**两种通道、四个档位全部 0-2 秒 `0xC0000094`**，
连窗口档也一样 → 不是渲染方式的问题，是环境 API 给游戏喂了坏值。

查我们自己的取证代码时发现一个真 bug：`GetDeviceCaps` 的 `VREFRESH` 常量写成了 **0**，
而 0 是 `DRIVERVERSION`（真实驱动返回 `0x4000` = 16384）——所以日志里那条「刷新率=16384」
是我们读错字段，**从来没测到过真实刷新率**，「刷新率=0 就改窗口档」的兜底也就从来没可能触发。
`VREFRESH` 的正确值是 **116**。已修；本机复测读数为 `刷新率=59`（桌面 60Hz），符合预期。
同时修正了 `DEVMODE` 结构（`dmPosition` 是 8 字节 POINTL + 4 字节 `dmDisplayFixedOutput`，
之前多塞了一个 `dmDisplayOrientation`，整体错位 4 字节）。
兜底写法**已作废**：当时写的是「只有真读到 0 时，才按 60Hz 重设一次」——本机永远读到 59/60，
那条重设分支一次都没执行过，客户机跑到的就是没验证过的代码（AGENTS 规则 24 第 10 条）。
现在改成**启动前无条件按 60Hz 设置、游戏退出后在 `finally` 里无条件还原**，每台机器同一条路径。

另外：客户那份日志里快照格式是「簇 703255439/总簇 66712107」，
和现在构建的「簇 总X/可用Y」不一致 → **他们跑的是旧版启动器**；旧版没有任何刷新率/磁盘的可靠读数。

1. 客户机上照常用「启动游戏」点一次，把那份 `运行日志.txt` 发回来就行。新日志里已经有：

   崩溃时还会自动带上系统崩溃报告里的**异常码 + 故障模块 + 偏移**（`崩溃捕获：…`，报告另存 `崩溃转储\`）。
   拿到模块+偏移就直接去反汇编那一条指令，不用再猜是哪个 API。
2. 快照里那台机器的游戏在映射盘 `X:\`，且出现过「可用簇 > 总簇」（703M vs 66.7M，数值不自洽）：

## 2026-11-07 网吧无盘 0xC0000094 崩溃：注册表缺值，已定案并修复

- **现象**：客户机（无盘 X:）点启动游戏 2 秒即退，退出码 0xC0000094（整数除零），两个画面档都崩；本机正常。

- **根因（客户机实证）**：无盘每次重启还原注册表，旧启动器只补 6 个值、且幂等判断只看 AppPath，其余 33 项长期缺失；导入完整注册表（tools\注册表修复.bat，39 项）后游戏立即恢复正常。

- **修复（按 bat 方案打进 game_starter.exe）**：
  1. 启动器一打开就写只读「注册表快照」日志：4 个位置（32/64 位 × ?III/®III）的键存在性、值数、AppPath/CDDrive、缺失值名，作为客户机判断依据；
  2. EnsureRegistry 升级：双键名都写、只写 32 位视图、完整 39 项默认值（= 本机实测全套，Test 三项=0，与 注册表修复.bat 完全一致）；缺啥补啥，玩家改过的值绝不覆盖，AppPath/CDDrive 与实际目录不符才校正；写不进只记日志不阻塞启动；
  3. 游戏退出后在日志里复查两键值数（判断游戏实际读哪个键）。
