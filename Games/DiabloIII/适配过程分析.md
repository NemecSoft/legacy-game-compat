# 暗黑破坏神III 夺魂之镰 终极邪恶版 · 适配过程分析

游戏：Diablo III: Reaper of Souls – Ultimate Evil Edition（CUSA00242，PS4 版 1.47 + 汉化 v0.9.6 + 六 DLC）
整合包：XDGAME 中文便携整合版 R1（SanctuaryPort 移植器，作者 CaduGimenes/SanctuaryPort）
游戏目录：`D:\Games\Diablo III Reaper of Souls - Ultimate Evil Edition`
工作区：`Games\DiabloIII\`

## 1. 整合包是什么

这不是 PC 原版暗黑3，而是 PS4 版的 PC 移植（SanctuaryPort，与战神3的 SpartanPort 同作者同框架）：
eboot.bin 在宿主机上直接重编译执行。目录结构：

- `game\CUSA00242\` —— 游戏本体（含 eboot.bin）
- `game\CUSA00242-UPDATE\` —— 1.47 更新（run.py 的 game_update 合成临时覆盖视图，不动两个原始目录）
- `bin\` —— sanctuary-probe.exe / sanctuary-play.exe 等移植器运行时
- `python\` —— 内嵌 Python 运行时（嵌入式，python.exe / pythonw.exe）
- `run.py` —— 完整启动编排脚本（「开始游戏.exe」就是它的打包壳）
- `patches\Diablo_III.xml`、`scripts\game_profiles.py` —— D3 专属补丁与运行参数

## 2. 启动链（run.py 干了什么）

1. `SANCTUARY_CONFIG` 默认指到 `<根>\sanctuary.ini`；图形选项（render_resolution / engine_fps /
   deferred_readback / stale_readback / async_shaders）从这读，游戏内画面菜单（Insert / R3+L2）
   也写回这。**没有 [节]，是平键值文件**。
2. sanctuary-probe `--cpu-features`：CPU 缺指令集时自动做 ISA 重写（exit 20 = 没救）。
3. game_update 把 `CUSA00242-UPDATE` 合并到本体上（目录链接视图，47 GB 级只花几个链接）。
4. game_profiles 的 D3 专属 env：`SANCTUARY_DEFERRED_READBACK=0`、`SANCTUARY_STALE_READBACK=0`、
   `SANCTUARY_VSYNC=0`（mailbox 呈现保 60 帧）、`SANCTUARY_DISABLED_OPTIMIZATIONS=12288`、
   `SANCTUARY_MENU_HIDE=vsync,engine_fps,readbacks`、允许分辨率 native/480p/720p/900p/1440p/1800p/4K。
   **这些是代码里定死的修复，不能也不需要从外部覆盖。**
5. d3_language：按 CPKs 里有的语言包选文本（整合包汉化替换了 enUS 资源）。
6. content_profile / prepare / link_libc / link_modules 之后拉起 sanctuary-play，run.py 陪跑到退出。

## 3. 「开始游戏.exe」逆向结论（2026-11-13，用户要求 REA 分析）

「开始游戏.exe」174,592 字节，MinGW-w64 编译的 C 薄壳（无 UPX，无加密）：

- 导入表只有 `CreateProcessW` + `WaitForSingleObject` + `GetExitCodeProcess` + `MessageBoxW` 等
  —— 取自身目录 → 起目标进程 → 阻塞等退出 → 回传退出码。
- 全部宽字符模板串（UTF-16LE 提取）：
  - `%ls\SanctuaryPort.exe`
  - `"%ls" --play%ls%ls`
  - ` SanctuaryPort.exe`、` - WWW.XDGAME.COM`（窗口标题 / 报错框用）
- **它不起任何服务器、不跑 python**：整个链路就是 `开始游戏.exe` → `SanctuaryPort.exe --play`。
- `SanctuaryPort.exe`（39 MB）是 Rust 写的官方启动器（panic 路径
  `F:\Codex\ChatGPT\SanctuaryPort-DiabloIII-Portable\build\vendor\wgpu-27.0.1\...`，内置
  多语言 GUI 文案）。`--play` 模式在启动器旁边找 runner 执行，错误文案
  `No runner next to the launcher (run.sh, or run.py on Windows)` 证实：它调
  整合包的 `python\python.exe` 跑 `run.py`——与本启动器直接设环境变量跑
  `python\python.exe run.py` 是同一条链，只少了 --play 那一层中转。

## 3.1 「要先启动服务器」的澄清

用户实测观察到 8788 端口有个 `python serve.py 8788`（系统 Python312，非整合包内嵌
python）进程，以为要先起它才能进游戏。排查结论：

- 整合包全目录树没有 serve.py；「开始游戏.exe」字符串里没有；SanctuaryPort.exe 里
  也没有（"8788" 是数字表 `...878879...` 的误命中，非端口）。
- 该进程 04:25:31 由别的程序拉起、04:41 自行退出，是机器上其它工具的本地服务，
  与游戏无关。
- **实机验证**：serve.py 已退出的状态下，game_starter.exe --go 走完整链，游戏窗口
  「暗黑破坏神3：夺魂之镰 – 终极邪恶版」正常出现、游戏本体加载 3.3 GB 内存——
  进游戏不需要任何服务器。

## 3.2 启动器（game_starter.exe）怎么接

- 探测（自愈式）：优先 `game\CUSA00242` / `game\CUSA00242-UPDATE`；缺失时在 `game\`
  和根目录扫一层含 eboot.bin 的目录（更新目录按名字带 UPDATE 识别）。结果记日志。
- 设 `SANCTUARY_GAME_DIR` / `SANCTUARY_PATCH_DIR` / `SANCTUARY_CONFIG` / `SANCTUARY_DATA_DIR`
  后启动 `python\python.exe run.py`（CreateNoWindow，不弹黑框），陪跑、退出码原样回传。
  进程树：平台 → game_starter.exe → python.exe → sanctuary-play。契约成立。
- **启动控制台**（2026-11-13 用户要求）：run.py / 移植器的 stdout、stderr 经重定向实时转发
  到主窗口底部的「启动控制台」面板（深底等宽字、自动滚动、保留最近 500 行）；启动器自己的
  日志也以 `▪` 前缀同步转推。实现：两条读线程收行进队列，UI 120ms 定时器批量粘贴；
  `PYTHONIOENCODING=utf-8` 统一 python（管道默认 GBK）与 probe（UTF-8）两边的输出编码，
  否则转码必乱。截屏实测：控制台随启动阶段滚动 Runtime 行，布局无错位。
- 「修复画面」= 写 `<根>\sanctuary.ini`：`display_mode=borderless`、`render_resolution=native`
  （幂等：相同不动、不同只改那一个键、缺文件带头注释新建）。不写 vsync/engine_fps/readbacks，
  理由见第 2 节第 4 条——写了会被 profile 盖掉。
- 键位**按战神III重制版方案注入**（2026-11-13 用户要求）：经 `SANCTUARY_KEY_MAP` 传
  `button=name` 逗号串（与战神3启动器同格式同解析代码，只是前缀 SPARTAN_ → SANCTUARY_）。
  按钮名以 probe 二进制里的按钮表为准（cross circle square triangle l1 r1 l2 r2 l3 r3
  options touchpad touchpad_left touchpad_right up down left right），战神3专属的
  rage/grab 等动作暗黑3没有，注入会被忽略。**实机验证**：`Runtime: pad map: 0 gamepad
  and 15 keyboard buttons remapped`，15 项全部接受、零 ignored，游戏正常进。
  l3/r3（走跑切换等）保留移植器默认 Z/X，不注入。

## 5. 已知取舍 / 风险

- 「开始游戏.exe」「SanctuaryPort.exe」原样保留；game_starter.exe 走的是同一条 run.py 链，
  行为一致。平台托管入口用 `game_starter.exe --go`。
- run.py 退出码是 python 壳的；游戏崩溃时 python 以非零码退出，平台可判。
- 首次启动着色器准备时间长（整合包 out\ 已带一份产物缓存，随包走）。
- sanctuary.ini 本次交付尚不存在（整合包没生成过），启动器「修复画面」会按移植器格式新建。
- 测试踩坑（2026-11-13 实测记录）：**上一局 run.py 没退干净就再启动，两个实例会在
  合并视图 / 着色器缓存上互踩**——表现为新实例中途被杀（退出码 -1）或 GPU 管线创建失败
  （vk_graphics_pipeline Critical）。不是键位注入的问题：清理干净后单实例带
  SANCTUARY_KEY_MAP 跑，游戏正常进（3.1 GB 内存稳定运行）。排查启动问题时先确认
  没有残留的 python.exe run.py。
